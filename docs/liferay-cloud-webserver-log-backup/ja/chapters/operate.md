# 7. 日々の運用
{: .no_toc }

1. TOC
{:toc}

## 目的

実行が失敗したときの対応、ログの検索方法、ログを読める人の管理、アクセスの多いサイトでの動作を把握します。

## 失敗と再実行

スケジュール実行が失敗すると、GitHub がワークフローの所有者にメールを送ります。チームに通知するには、ワークフローの最後にコメントアウトしてある `notify` ジョブを有効にし、Slack、Teams、メールなどの宛先を設定してください。

いずれかの時間が失敗すると、その実行は失敗扱いになりますが、他の時間は実行を続けます。その実行を開いて **Re-run failed jobs** を使ってください。再実行では `plan` ジョブが確定した日付をそのまま使うため、その時間が Liferay Cloud の 30 日の保持期間内にある限り、同じ日をバックアップします。代わりに * 新しい * 実行を開始すると、その新しい実行の前日分をバックアップします。

一時的な API エラーなどで `lcp log` が途中で失敗した場合、スクリプト自体が 60 秒間隔で最大 3 回まで再試行してから、ジョブを失敗させます。

## ログの検索

一度だけの調査には、`aws s3 cp` と `zgrep` を使います。定期的に分析する場合は、バケットのプレフィックスに対して Amazon Athena のテーブルを定義してください。`year=/month=/day=` フォルダがパーティションとして機能するため、1 日分のクエリではその日のファイルだけを読み込みます。

## アクセス管理

ログには、クライアントの IP アドレスやリクエストの URL が含まれ、プライバシー関連の法律では個人情報に当たる場合があります。バケットの読み取り権限は必要な人だけに限定し、保持期間はプライバシーポリシーに合わせて設定してください。

## 認証情報

サービスユーザーのパスワードを変更したら、同時にシークレット `LCP_PASSWORD` も更新してください。パスワードが間違っていると、すべての実行が *Authenticate LCP CLI* ステップで失敗します。

## 大量のログ {#large-volumes}

10,000 行ごとに 1 回のリクエストと 3 秒の待ち時間がかかり、さらにダウンロード時間（実測で毎秒約 850 行）が加わります。たとえば 1 分あたり 11,000 行（1 日あたり約 1,600 万行）の場合：

- 1 日分を 1 つのジョブで取得すると、約 1,600 回のリクエストと推定 5〜7 時間がかかり、GitHub ホストランナーのジョブ上限である 6 時間を超えます。
- 1 時間分は約 66 万行、66 回のリクエストで、1 ジョブあたり推定 15〜20 分です。4 つずつ並行して実行すると、1 日分はおよそ 1.5〜2 時間で終わります。
- S3 には 1 日あたり約 500 MB の gzip ファイルが保存され、ランナーを数 GB のテキストが通過します。

これらは小規模な環境での測定に基づく推定値です。本番開始前のテストで実際の実行時間を測り、`max-parallel` を増やす場合は Liferay Cloud のサポートの同意を得てください。このレベルのログ量が続く場合は、ログを書き込まれた時点でストリーミングすることも検討してください（後述）。

## アクセスログ以外の行を残す

抽出処理では、nginx の警告や起動時のメッセージなど、アクセスログのタイムスタンプがない行は削除されます。これらも残すには、取得した生のログも（時間の境目で一部重複させて）アップロードするか、ログをストリーミングしてください。

## オプション：リアルタイムのストリーミング

Splunk、Datadog、Elastic などのログ基盤にほぼリアルタイムで送るには、プロジェクトリポジトリのカスタム設定ファイルで、`webserver` サービスの nginx から syslog でアクセスログを送信することもできます。

```nginx
access_log syslog:server=logs.example.com:514,tag=liferay_web combined;
```

{: .warning }
nginx の syslog 出力は UDP を使うため、行が失われることがあり、暗号化もされません。同じプロジェクト内のフォワーダー（例：カスタムサービスとして動かす Vector や Fluent Bit）に送り、そこから TLS でログ基盤へ転送してください。カスタムサービスと外部への通信が許可されているかは、Liferay Cloud のサポートに確認してください。

ストリーミングには 1 日の遅れがなく、30 日の保持期間にも左右されません。S3 へのバックアップは、独立したアーカイブとして残してください。

## 確認

失敗通知の届き先、バケットを読める人、サービスユーザーのパスワードを次に変更する日、そしてお使いの環境で 1 日分の実行にかかる時間が分かっていれば完了です。
